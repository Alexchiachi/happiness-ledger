# 雙帳本協定

> **這份文件由兩邊共同持有。**
> 台灣端與中國大陸端各自獨立運作、各自由不同的 AI 或團隊維護，
> 靠這份協定對齊 —— 而不是靠人在中間口頭傳話。
>
> 讀完這份，你應該能**只做自己那一半**，而且知道對方會做什麼、不會做什麼。

---

## 一、為什麼是兩本帳本

台灣端的存入流程經過 `script.google.com`，該網域在中國大陸無法連線。
大陸訪客開得了網頁，卻送不出紀錄。

已評估並排除的單一帳本方案：中繼改用境內雲端（中繼自身出境連 `api.github.com` 同樣不穩）、
中繼部署香港（連通性無保證）、境內主機加自訂網域（需 ICP 備案）。

因此改為**兩本獨立帳本，加上定期單向遷移**。

---

## 二、角色與所有權

| | **甲方：中國大陸端** | **乙方：台灣端** |
| :--- | :--- | :--- |
| 系統 | 境內自建，技術自選 | `Alexchiachi/happiness-ledger` |
| 對誰開放 | 大陸訪客 | 其餘地區訪客 |
| 帳本地位 | **分帳** —— 區域收集點 | **總帳** —— 最終典藏 |
| 呈現範圍 | 只呈現自己收到的紀錄 | 呈現全部紀錄（含甲方遷移過來的）|
| 交付物 | 符合契約的匯出檔 | 匯入結果的回報 |

### 這個不對稱是刻意的

**乙方會收下甲方的紀錄；甲方不會收乙方的。**

原因是方向的可靠性不同：乙方（境外）主動去讀甲方的資料是通的；
甲方（境內）主動連 GitHub 則時通時不通。把不可靠的方向從流程裡拿掉，
整條路才穩。

因此「合併統一」的意思是：**所有紀錄最終都會在乙方的總帳裡**。
甲方的帳本持續運作、持續收件，但它呈現的永遠是自己那一部分。

---

## 三、唯一的耦合點

**兩邊只透過一樣東西相連：匯出檔。**

其格式定義在 [`docs/CN_LEDGER_SPEC.md`](./CN_LEDGER_SPEC.md) 第三節〈資料契約〉，
**那是唯一的權威來源**。本文件不重述欄位定義 —— 同一份 schema 寫在兩個地方，
遲早會走鐘。

除了這個檔案的格式之外，兩邊**沒有任何其他約定**：
甲方用什麼語言、什麼框架、什麼雲端、資料庫長什麼樣，乙方一律不管也不該假設。

---

## 四、各自不可以假設的事

這一節是兩個獨立系統最容易出事的地方。

**甲方不可以假設**

- 乙方能即時看到甲方的資料 —— 遷移是**定期批次**，不是同步
- 紀錄送出後會馬上出現在總帳 —— 中間隔著一次人工匯出
- 乙方會替甲方修正格式錯誤 —— **不合格的匯出檔會被整批退回**
- 自己能連上 GitHub —— **不要設計任何需要連 GitHub 的功能**

**乙方不可以假設**

- 匯出檔是最新的 —— 它是某個時間點的快照
- 匯出檔只含新紀錄 —— 它是**完整快照**，去重是乙方的責任
- 甲方的時鐘與自己一致 —— 一律以匯出檔中帶時區的 `date` 為準
- 甲方會保留已刪除的紀錄 —— 快照中消失的紀錄，總帳**不會**跟著刪除

**兩邊都不可以假設**

- 對方的編號空間 —— 乙方的 `id` 是 GitHub Issue 編號（整數），
  甲方的 `id` 必須是字串。這條規則存在的唯一目的就是防止相撞

## 五、交接流程

```
【甲方】匯出完整快照 ──► 匯出檔.json
                              │
                              ▼
                    【甲方 → 乙方】交件訊息
                              │
                              ▼
【乙方】驗證（--dry-run）─── 不合格 ──► 退件訊息 ──► 回到甲方
                              │
                            合格
                              ▼
【乙方】逐筆建立 Issue（間隔送出）
                              │
                              ▼
      既有流程寫入 records/*.md + ledger.json
                              │
                              ▼
                    【乙方 → 甲方】完成訊息
```

**節奏**：由乙方發起，建議每月一次。甲方不需要主動推送。

## 六、交握訊息格式

兩個 AI 之間**實際要說的話**。照這個格式，對方能直接處理，不必來回追問。

### 甲方 → 乙方：交件

```
【幸福記帳本 · 匯出交件】
匯出時間：2026-10-01T12:00:00+08:00
快照範圍：全部紀錄（完整快照）
紀錄筆數：128
最早一筆：2026-09-05T08:12:00+08:00
最新一筆：2026-09-30T22:41:00+08:00
檔案：ledger-cn-20261001.json
自我檢查：
  - 所有 id 皆為字串，格式 cn-<日期>-<序號>          ✅
  - 所有 date 皆帶時區                                ✅
  - 已依內容準則人工審核，移除 N 筆不符者              ✅
備註：（若無則寫「無」）
```

### 乙方 → 甲方：退件

```
【幸福記帳本 · 匯入退件】
檔案：ledger-cn-20261001.json
結果：驗證未通過，整批未匯入
問題：
  - 第 17 筆：date 缺少時區（"2026-09-20 14:30"）
  - 第 42 筆：id 為數字 42，必須是字串
處理：請修正後重新匯出完整快照，不需只送差異
```

### 乙方 → 甲方：完成

```
【幸福記帳本 · 匯入完成】
檔案：ledger-cn-20261001.json
本次新增：31 筆（已略過先前匯入的 97 筆）
對應 Issue：#124 – #154
總帳現況：共 183 筆
下次預定：2026-11-01
備註：（若無則寫「無」）
```

**退件是整批的。** 128 筆裡有 1 筆格式錯誤，就是 128 筆都不匯入。
這是刻意的 —— 匯入一半會讓兩邊的狀態難以對帳，遠比重跑一次麻煩。

## 七、出錯了算誰的

| 症狀 | 歸屬 | 處理 |
| :--- | :--- | :--- |
| 匯出檔驗證失敗 | 甲方 | 乙方退件，甲方修正後重新匯出完整快照 |
| 同一筆重複出現在總帳 | 乙方 | 檢查 `tools/imported-ids.json`；正常情況下 `source` + `id` 會擋掉 |
| 遷移紀錄的日期變成遷移當天 | 乙方 | 解析器未讀到 `原始存入時間`，檢查 Issue 內文格式 |
| 遷移紀錄的時間差 8 小時 | 甲方 | `date` 缺時區被當成 UTC，甲方修正後重送 |
| 匯入中途失敗 | 乙方 | 清單已存檔，修正後重跑會從中斷處繼續 |
| 甲方帳本收不到紀錄 | 甲方 | 與乙方無關，乙方不介入 |
| 總帳的卡片牆時序錯亂 | 乙方 | 檢查 `ledger.json` 是否依 `date` 新到舊排序 |

**原則**：匯出檔之前的問題是甲方的，之後的是乙方的。

## 八、契約要改怎麼辦

**任何一方都不得單方面變更 [`CN_LEDGER_SPEC.md`](./CN_LEDGER_SPEC.md) 第三節。**

它是兩邊唯一的介面，單方面更動會讓遷移**在無聲中出錯** ——
資料看起來有進來，但時間錯了、或編號撞了、或整批被退。

變更程序：

1. 在 `Alexchiachi/happiness-ledger` 開一個 issue，說明要改什麼、為什麼
2. 雙方確認影響範圍（尤其是已匯入的舊資料要不要回填）
3. 以 PR 修改規格，並同步更新 `tools/import-records.js` 的驗證邏輯
4. 合併後兩邊各自更新，下一次交接才適用新契約

**新增可選欄位**通常安全（舊資料沒有該欄位仍可通過驗證）。
**修改或移除既有欄位**必定破壞相容性，需要明確的回填計畫。

## 九、各自的驗收清單

### 甲方：匯出前

- [ ] 匯出檔最外層是陣列
- [ ] 所有 `id` 為字串，且不可能與整數混淆
- [ ] 所有 `date` 帶時區；抽驗一筆，換算後與實際存入時間相符
- [ ] 已依 `CONTRIBUTING.md` 的內容準則審核
- [ ] 快照為完整快照，非差異

### 乙方：匯入前

- [ ] `node tools/import-records.js <檔案> --dry-run` 通過
- [ ] 待匯入筆數與甲方交件訊息中的數字相符
- [ ] 抽查一筆的時區換算結果

### 乙方：匯入後

- [ ] `data/ledger.json` 可正常解析，筆數增加符合預期
- [ ] 抽查一筆遷移紀錄：`date` 為原始時間、`source` 與 `origin_id` 存在
- [ ] 卡片牆依時間新到舊排列，遷移進來的舊紀錄未置頂
- [ ] Actions 全綠，每筆存入只有一個 run
- [ ] 已 commit `tools/imported-ids.json`

## 十、給接手的 AI

**若你是甲方**：讀 [`CN_LEDGER_SPEC.md`](./CN_LEDGER_SPEC.md)（建置規格）與
[`CONTRIBUTING.md`](../CONTRIBUTING.md)（內容準則）。第三節的資料契約是硬性的，
其餘皆為建議。**不要嘗試連接 GitHub。**

**若你是乙方**：讀 [`CLAUDE.md`](../CLAUDE.md)（專案脈絡，含「不要做的事」）與
`tools/import-records.js`。遷移只走 Issue，**不要直接改寫 `data/ledger.json`**。

**兩邊都請記得**：這是一件行為藝術作品，承諾是「恆久銘記」。
判斷取捨時，「使用者的文字絕不遺失」與「狀態必須說真話」的優先序，
高於效能與程式碼美感。

有疑義時，寧可停下來問，不要猜。**猜錯的代價是別人的一段真心話消失，
而且沒有人會發現。**
